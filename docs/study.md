# Benchmark study on Groq's free tier (plan M)

Plan M was approved on 2026-11-20. Configs are generated by
`scripts/make_study_configs.py` into `configs/study/` (and the day-1 pilot into
`configs/pilot/`). Regenerate after editing the tables in the script.

## Daily routine

```sh
scripts/daily.sh configs/pilot/schedule.toml   # day 1 (pilot)
scripts/daily.sh                               # days 2–11 (configs/study/schedule.toml)
uv run ask-or-act study status configs/study/schedule.toml   # any time; calls nothing
uv run ask-or-act audit-redaction              # after each day
```

`study run`:
- groups the schedule's configs into one queue per model, then runs the queues in
  parallel;
- skips configs that already completed;
- stops a model cleanly at its daily limit (exit 5 from that run);
- prints a progress summary at the end. Per model, the summary shows:
  - decisions done / total;
  - requests and tokens used today (from each run's `api_usage`);
  - the provider's last remaining-requests count;
  - the calls and tokens still needed;
  - the estimated days left at 90% of the limits.

## What keeps quota use down

- **Subsets are nested**, by seeded order:
  - `per_label = N` for Banking77;
  - `limit` + `stratify = "label"` for Aegis;
  - `limit` + `stratify = "question"` for MT-Bench (whole questions).

  A smaller subset is always inside a larger one.
- **Main calls are cached on their own.** A self-consistency config (`samples = 3`)
  reuses the main calls that the main-only config (`samples = 0`) made. The plan's
  estimate and `study status` account for this.
- **Identical inputs share one call within a run.** On MT-Bench, several judges voted on
  the same comparison: a full half (500 votes) needs 361 calls. (Comparisons shown
  with the two models in swapped order are different prompts, so 274 comparison ids
  give 361 distinct inputs.)

## Pilot (day 1, 2026-11-21 UTC) and the plan changes it led to

The pilot ran 20 test examples per dataset (`configs/pilot/`, kept as the record of
what ran; the generator no longer rewrites them). Approved changes for days 2+:

1. **gpt-oss-120b and gpt-oss-20b on Banking77 use `response_format = "json_object"`**
   (main and self-consistency). The 78-option answer schema is then not written into
   the prompt: 640 instead of 1,060 input tokens per call. In the pilot, 0/20 answers
   were invalid and 19/20 matched the strict-schema answers. The server no longer
   validates the label, so invalid answers are monitored (below).
2. **qwen3.8-27b samples at temperature 0.7** (0/60 failed samples, against 17/95 at 1.0).
3. **Expected output tokens from the pilot:** gpt-oss Aegis 45, gpt-oss-120b MT-Bench 85,
   qwen Aegis 15, qwen MT-Bench 16.
4. **`input_overhead_tokens = 97`** for the json_object configs: an estimate-only
   setting (not in the cache key) for the tokens Groq adds per call in that mode.
5. **Self-consistency stays k = 3 with shuffled + reworded prompts**, as designed. Not
   re-tuned on 20 examples.
6. **`scripts/daily.sh` runs unbuffered**, so an interrupted session still leaves a log.

None of these touch the frozen guarantee settings (docs/guarantees.md).

## Invalid-output stop rule (approved 2026-11-21 UTC)

- Every `study status` / `study run` summary shows, per model:

  `invalid outputs X/Y (Z%; main a, samples b)`

  It counts every model output in the schedule's runs once: main answers and
  self-consistency samples, by provider response id. An invalid output is one that
  failed the provider's JSON validation, or an answer that isn't one of the options.
- **If a model goes above 2%,** its queue stops with "STOPPED: … ABOVE THE 2% LIMIT".
  It is checked before and after each config, so the stop holds on later days, and
  that model makes no further calls until the author decides. The other models
  continue.

## Reporting rule for test results (pre-registered 2026-11-21 UTC, before day 2)

The pilot and the smoke runs looked at 20 test-half examples per dataset, and two
settings were chosen from them (json_object for gpt-oss on Banking77, qwen's sample
temperature). So every final **test-half** result is reported twice:

- **Primary:** the full test half, as planned.
- **Sensitivity check:** the test half **excluding the seen examples**. Their ids are
  listed in [`configs/pilot/seen_test_ids.json`](../configs/pilot/seen_test_ids.json):
  20 per dataset, the same 20 in every smoke and pilot run. For MT-Bench's
  per-comparison analysis, every comparison that contains a seen vote is excluded:
  20 comparisons, 48 test votes.

The calibration half was never used in the smoke or pilot runs, so thresholds are fit
on untouched data. Banking77's target registration came ~7 minutes after the first
Banking77 pilot calls; this is disclosed in docs/guarantees.md and is not changed.

## Study freeze (2026-11-22 UTC, before day 2, until the study ends)

The study and pilot configs, and the code that resolves them into requests and cache
keys, are frozen. `tests/test_study_freeze.py` pins four hashes per config (44
configs) in `tests/fixtures/study_freeze.json`:

- resolved settings, i.e. everything in the cache keys;
- the request bodies for a synthetic example;
- the selected example ids;
- the config file.

CI fails if a code change alters any of them. Re-pinning needs the author's approval.
The pinned settings match the decider config recorded in every pilot run's `run.json`.

## Scheduled runs (launchd, from 2026-11-22 UTC)

`scripts/study-job.sh` runs the study once a day without asking, as a macOS launchd job.

**When it runs:**
- At 10:00 local time, at most once per UTC day. Groq's daily limits reset at 00:00 UTC.
- A 10:00 missed while the Mac slept runs on wake. One missed while it was off runs at
  the next login, and an hourly check backs that up.
- Any study log started that UTC day counts as the day's run, including a manual
  `scripts/daily.sh` run, so a run is never repeated.
- If a study run is already in progress, the job skips.

**Isolation from development:** the job runs from a separate git worktree,
`~/Developer/ask-or-act-study`, checked out at the newest `study-v*` tag.
- Editing, switching branches or leaving uncommitted work in the main folder can't
  affect it.
- Its `runs/`, `.cache/`, `logs/`, `data/raw/` and `.env` are symlinks to the main
  folder's. So there is one cache and one set of runs, and nothing is duplicated or
  re-paid.
- Before any call, preflight checks all of the following. If any check fails,
  nothing is called and you get a notification.
  - the worktree is clean and exactly at the newest `study-v*` tag;
  - the shared folders are linked;
  - `.env` contains `GROQ_API_KEY` (checked by name only);
  - every config is free tier with `max_usd = 0`;
  - `tests/test_study_freeze.py` passes.

**What a run does:** `study run --yes` with the usual guards (budget, the 2% invalid-
output stop, the quota stop), then `audit-redaction runs .cache logs`. The log
`logs/<UTC time>-schedule.log` ends with a summary block: the study's exit code, the
audit result and `result: OK` or `ATTENTION: …`.

**When you get a notification:** a model STOPPED, the study errored, the audit found
something or errored, a preflight check failed, or the job aborted. Reaching the
daily limit is normal and doesn't notify.

```sh
scripts/study-job.sh today     # did today's (UTC) run happen, and how did it end?
scripts/study-job.sh summary   # the latest run's result
scripts/study-job.sh remove    # unload the job, delete its plist and the worktree
                               # (runs, cache, logs and tags are kept)
scripts/study-job.sh setup     # create the worktree, or move it to the newest pin
scripts/study-job.sh install   # (re)write the plist and load the job
```

**Moving the pin (only if the study code itself needs a fix):**
1. Fix it in the main folder and commit. CI must pass, including
   `tests/test_study_freeze.py`. The freeze test is the guard: if the fix changed
   any config's resolved settings, request bodies or selected ids, it fails. It is
   never re-pinned without the author's approval.
2. Tag the fixed commit with the next number and the reason:
   `git tag -a study-v2 -m "why" <commit>`.
3. `scripts/study-job.sh setup` moves the worktree to `study-v2` and syncs its
   environment. Then run `scripts/study-job.sh install`, so the plist matches.
4. Record the move and its reason in this file.

Between steps 2 and 3, every run refuses with "not at the pin". So a new tag can't be
picked up silently, and a forgotten move can't run old code unnoticed.
